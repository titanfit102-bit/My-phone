# My Phone Engine v1 — Architecture and Verification

**Status:** Phase 1 (Engine Core) is implemented on a separate draft PR only; remaining phases are proposed. This document describes the intended design, not a released Production capability.

**Parent chain:** \`main\` → PR #12 (isolated ZIP Quick Preview) → PR #13 (premium workspace) → Engine Core PR. Do not merge out of order or promote Production without a separate release decision.

## Product job

A private, browser-based control center for owner-managed app previews. For each user-provided source, report **what the source is**, **which preview route is supported**, **what is verified**, and **what the user should do next**. The Studio must never claim that identifying a framework means a build ran or an application loaded.

**Non-goals for v1:** universal ZIP-to-running-app conversion; executing raw sources in Studio's origin; backend/SSR/database emulation; automatic native APK generation; unattended cloud code execution; storage of third-party app source in the Studio repository; AI code modification.

## Verified baseline

- Central Expo + React Native Web frontend hosted in the existing Vercel project, source in \`studio/\`.
- Saved projects are browser-local references (\`my-phone-studio-projects-v1\`), with JSON export/import. This is **not** a hosted application registry.
- Published Web URL iframe; published revision observation through \`/build-info.json\`, 15-second polling, 60-second unverified fallback, and Session Freeze.
- Android mode embeds an **already published Appetize build**; the Studio does not build or upload APKs.
- PR #12's ZIP Quick Preview interprets a supported **prebuilt, single-JS-bundle** ZIP inside an opaque-origin sandboxed, network-blocked iframe. It does **not** compile source.
- PR #13's premium three-column desktop layout. Its head passed 49 Node tests and 31 executed Playwright cases (+ 1 intentionally skipped mobile-only applicability), before this engine branch.

### Phase 1 — deterministic Engine Core (this PR)

Files:
- \`studio/src/zip-inspector.js\`: read-only ZIP metadata and validated, normalized paths; emits exact Web build entrypoint candidates independently of framework classification.
- \`studio/src/engine-core.js\`: pure decision logic; converts validated ZIP metadata plus **actual renderer outcome** to a typed/structured assessment. Does not decompress, build, execute, fetch, persist, or upload code.
- \`studio/src/ZipImportPanel.web.tsx\`: displays a small Engine Core assessment alongside existing upload feedback; keeps sandboxed renderer and existing error/close semantics unchanged.
- \`studio/tests/engine-core.test.mjs\`: Node test matrix for candidate, source-only, multiple entrypoints, failed render, prepared preview, native and unknown inputs.

Contract: \`assessZipInspection(inspection, attempt)\`, where \`attempt.status\` is \`not_attempted\`, \`prepared\`, or \`failed\`. The only acceptable signal for \`prepared\` is a successful \`buildQuickPreview\` return. **Prepared means the isolated HTML payload was generated, not that the iframe visibly rendered or that all app features work.** A matching \`dist/index.html\` alone is only a candidate.

An inspection's \`buildCandidateCount\` and \`buildCandidates\` are advisory metadata, bounded and derived from validated paths, not an executable entrypoint. \`kind=source\` can coexist with a prebuilt \`dist/\` folder: the engine must not treat framework classification as the authoritative render decision.

Assessment statuses:
- \`candidate\`: exactly one built Web entrypoint found; renderer validation not yet complete.
- \`prepared\`: compatible isolated payload generated by existing renderer.
- \`build_required\`: source-only project with no built Web entrypoint.
- \`native_build_required\`: Android source without APK or Web artifact.
- \`unsupported\`: no supported artifact, or multiple Web build roots.
- \`failed\`: renderer rejected an artifact; never show it as running.

Diagnostics have stable machine codes, concise descriptions, and user next actions; messages are ordinary text, not HTML.

### Phase 2 — Advanced ZIP Engine (future PR)

Support additional local assets only with a constrained asset graph, verified hashes, strict resource budgets (compressed/uncompressed), explicit caps on entry and dependency count, and opaque-origin iframe isolation. Start with a test fixture, not an assertion that arbitrary chunked ESM or network APIs can be made to work offline.

**Security gate:** no \`allow-same-origin\` on \`srcDoc\` + \`allow-scripts\` frames; no unpacking to public Studio origin; no browser-origin bridge, token, unbounded decompression, unsafe URLs, remote backend or package install. Unknown scripts are not interpreted until explicit review of their sandbox behavior.

### Phase 3 — Diagnostics (future PR)

Stable error taxonomy for corrupt/encrypted ZIP, malformed path, unsupported build, missing asset, CSP/iframe prohibition, unpublished Web URL and unverified remote metadata. No false "build succeeded" inference from URL reachability. Avoid leaking private file paths, tokens, or arbitrary stack traces.

### Phase 4 — GitHub Auto Preview (future PR)

Read-only provider status and app deployment metadata **first**. Existing manifest polling can observe an app's published revision but **cannot prove private CI success**. Private CI checks require narrowly scoped, server-side credentials, authorization design, request quotas and an audit trail. Do not put provider secrets in React Native Web, project URLs, localStorage, or manifests.

Source-to-build is a **separate later system** requiring isolated ephemeral workers, explicit per-execution authorization, resource/runtime quotas, build provenance, supply-chain checks, output isolation and budget caps. GitHub link alone never triggers a build.

### Phase 5 — acceptance and release

Required evidence:
1. Unit cases cover every decision state plus source-with-dist, ambiguity, invalid inputs and no-mutating behavior.
2. Full \`npm run check:config\`, \`npm run typecheck\`, \`npm run export:web\`, \`npm run test:e2e\` on the exact branch head.
3. Browser: existing Web, Appetize link, JSON backup, Session Freeze, ZIP sandbox and mobile controls remain functional.
4. User-owned representative ZIP receives accurate diagnostics; preview success isn't confused with backend/API success.
5. Threat review of ZIP handling, decompression limits, sandbox/CSP, external resources and output size.
6. Security advisories must be triaged: current baseline had High vulnerabilities under temporary exception, expiring 2026-11-21. Green CI alone does not equal clean audit.
7. Preview deployment SHA verified; human visual acceptance; **explicit separate authorization** before a Production merge, deployment, or introducing billable services.

## Architectural decision records

**ADR-01: pure JavaScript core before cloud executor**
- Decision: deterministic, zero-dependency function, inside existing Studio repository.
- Why: compatible with local user workflow, cheap, testable, no extra secret-bearing service.
- Alternative: server-side build service on first iteration; rejected due to execution risk and operational cost.
- Revisit: when there is a validated source-only build demand and secure worker design.

**ADR-02: classify ≠ render ≠ run successfully**
- Decision: inspector identifies candidates; renderer produces payload; actual application correctness requires separate browser and backend acceptance.
- Why: a source archive can contain \`dist/\`; an \`index.html\` can exist without valid assets.
- Revisit: never remove this boundary.

**ADR-03: source stays isolated**
- Decision: outside projects and their CI/build credentials stay outside \`My-phone\`.
- Why: prevents accidental cross-project edits and credential leakage.
- Revisit: integration proxies only with scoped provider grants and logging.

## Costs

Core classification and already-supported offline ZIP preview add **no new paid provider or npm dependency**. Running full CI still uses account quotas. Future Android sessions, isolated build runners, private provider integrations, storage and AI agents may incur usage charges and require separate budget approval.

## Operational status and stop gates

This document and Phase 1 branch are **not** Production. Keep the PR draft while dependencies (PR #12 and PR #13) are unmerged. Never alter \`main\`, Studio Production, another project repository, provider secrets or project settings as a side effect of implementing this plan.
